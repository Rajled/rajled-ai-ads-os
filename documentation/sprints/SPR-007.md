# Sprint S1-007 - Google Ads Account Discovery and Selection

**Status:** ACCEPTED

**Release:** v0.2.0-alpha.4

**Final Accepted Commit:** `53ca13e`

---

## Sprint Goal

Discover accessible Google Ads accounts and their metadata, translate them into provider-neutral application models, and allow an administrator to persist a validated active client account.

---

## Completed Work

### Accessible Account Discovery

`GoogleAdsAccountDiscovery` calls `ListAccessibleCustomers` and converts each valid resource name into the integration-owned `AccessibleGoogleAdsAccount` DTO.

The DTO contains only:

- resource name;
- customer identifier.

It is not a Domain entity and does not expose credentials or native SDK objects.

### Account Metadata Discovery

`GoogleAdsAccountDetailsReader` uses Google Ads API V24 queries inside the SDK boundary to retrieve:

- account descriptive name;
- resource name and customer identifier;
- Manager or Client classification;
- managed-account hierarchy and access path.

Every directly accessible root is queried with a client scoped to that root as `login-customer-id`. The same root-scoped client is reused when traversing that root's manager hierarchy.

### Provider-Neutral Application Model

`GoogleAdsAccountCatalog` maps Google Ads detail results through `GoogleAdsAccountMapper` into `AccountCandidate` objects.

The provider-neutral application contracts and services are:

- `AccountCandidate`;
- `AccountCatalogInterface`;
- `AccountSelectionService`;
- `ActiveAccountStoreInterface`.

The catalog preserves deterministic deduplication and canonical access identifiers. Directly accessible roots retain no access-account identifier; managed clients retain the manager identifier required for future access.

### Dashboard and Persistence

`GoogleAdsAccountPanel` provides administrator-only, nonce-protected POST actions for discovery and selection.

- Ordinary GET requests perform no Google Ads API operation.
- Discovery occurs only after the administrator requests it.
- Managers are visible but cannot be selected.
- Client accounts are selectable.
- Selection performs fresh canonical discovery before persistence.
- Invalid, unavailable, stale, manager, unknown, or ambiguous selections are rejected.

`GoogleAdsActiveAccountStore` implements `ActiveAccountStoreInterface` with a validated, non-autoloaded WordPress option. Only non-secret account selection data is stored.

## Production Diagnosis

Live acceptance revealed that `ListAccessibleCustomers` returned seven directly accessible roots, while three cancelled roots rejected subsequent detail queries with `PERMISSION_DENIED`.

The original fail-fast loop stopped discovery after the first inaccessible root. That prevented usable client roots and an active manager hierarchy from being discovered.

The production environment contained seven directly accessible accounts, including three cancelled accounts, one active manager account, and three active client accounts. This real-world topology drove the redesign of the discovery pipeline and validated the need for explicit partial discovery semantics.

Root-scoped client construction was also corrected so each directly accessible root is queried with its own root identifier rather than a login-free client.

## Partial Discovery

The accepted design introduces explicit immutable result models:

- `AccountDiscoveryResult` in Application;
- `DiscoveryCompleteness` with `COMPLETE`, `PARTIAL`, and `EMPTY` states;
- `GoogleAdsAccountDetailsDiscoveryResult` in Google Ads Integration;
- `GoogleAdsAccountDiscoveryFailurePolicy` in the SDK boundary.

A root can be skipped only when the failure:

- is a `GoogleAdsSdkException`;
- occurred during `root_account_query`;
- is classified as a recoverable root-scoped permission failure;
- does not prevent processing another independently accessible root.

Systemic failures remain fatal, including:

- client initialization and authentication failures;
- OAuth failures;
- `ListAccessibleCustomers` failures;
- invalid queries;
- malformed responses;
- transport failures;
- manager hierarchy failures;
- mapping, deduplication, and persistence failures;
- unexpected exceptions.

If all non-empty roots are unavailable, discovery fails. If some roots succeed, the result is explicitly `PARTIAL` and includes only a bounded unavailable-root count. No hidden mutable recovery state is used.

The dashboard renders usable accounts and a sanitized partial-discovery warning. Partial logs contain only the operation, partial outcome, and unavailable-root count.

## WordPress Acceptance

Acceptance in the production-like WordPress hosting environment confirmed:

- four usable accounts were displayed after three cancelled roots were omitted;
- one manager account remained visible and unselectable;
- three client accounts were selectable;
- a designated client account was selected successfully;
- the selected account remained active after page refresh;
- no normal GET request triggered account discovery;
- no credentials, failed-root identifiers, or raw API responses were exposed.

The selected production account name is intentionally omitted from documentation.

## Architecture Outcome

Sprint S1-007 established the first provider-neutral account discovery and selection workflow.

```text
Google Ads API
    -> SDK-bound Google Ads readers
    -> Google Ads integration DTOs
    -> GoogleAdsAccountCatalog
    -> AccountDiscoveryResult / AccountCandidate
    -> AccountSelectionService
    -> ActiveAccountStoreInterface
    -> WordPress option adapter
```

Domain remains provider-independent, native SDK types remain under `Integration/GoogleAds/Sdk`, and WordPress persistence is isolated behind an Application contract.
